## 当前实现

应用已从零实现最小 Library 接入和浏览流程：

| 模块 | 位置 | 当前职责 |
| --- | --- | --- |
| 模型 | `model/Entry.kt`、`model/Index.kt` | 目录条目、媒体类型和索引序列化 |
| 存储 | `storage/LibraryTree.kt`、`storage/LibraryStore.kt` | SAF 目录读取、`.gallery/index.json` 缓存和 `RULES.md` 写入 |
| 媒体 | `media/MediaProbe.kt` | 读取图片 EXIF 和视频容器元数据 |
| 扫描 | `scan/Scanner.kt` | 读取 `相册/` 直属文件与 `画集/*/` 直属文件，报告不规范内容 |
| 界面 | `ui/` | 相册网格、画集项目列表、项目详情、右侧滑块和系统查看器/播放器调用 |

接入后先展示缓存，再进行后台增量扫描；扫描只读取 `size` 或修改时间变化的文件。应用不修改任何媒体文件。

## 内置查看器（已定方向，尚未实现）

当前代码里**没有**查看器：点击媒体仍然只是交给系统应用，`ui/OpenWith.kt` 仍写着「Rem 不内置自己的查看器」。本节记录的是已确认的方案与实测依据，不是已实现的能力。

### 内嵌方案

| 用途 | 方案 |
| --- | --- |
| 视频播放 | `androidx.media3:media3-exoplayer:1.11.1` + `media3-ui:1.11.1` |
| 图片查看 | `me.saket.telephoto:zoomable-image-coil3:0.19.0` |
| 连续翻页 | Compose Foundation `HorizontalPager`，`beyondViewportPageCount = 1` |

Telephoto 0.19.0 的传递依赖为 Coil 3.2.0、Kotlin 2.1.21、Compose runtime 1.8.0，与本项目现状（Coil 3.2.0 / Compose BOM 2025.04.01 的 1.8.0 线）一致；Media3 1.11.1 的 Compose 构件 `media3-ui-compose-material3` 在 Google Maven 实测存在，其 `kotlin-stdlib:2.2.10` 在本项目 Kotlin 2.1.20 下编译无警告。

### 实测依据

以下数据来自仓库外的独立探针工程（`dev.susnowy.remprobe`，与被测库同版本栈，**不属于本仓库**，因此不能用 `./gradlew :app:testDebugUnitTest` 复现）。设备为真机 `baff50eb`（23127PN0CC，Android 16 / API 36，arm64-v8a）与模拟器 `Rem_API_36`（API 36，x86_64）。所有操作通过界面与 `adb` 完成。

**图片：降采样成立**。Coil 的 `ImageResult.SuccessResult.isSampled` 是直接证据，不需要从尺寸推断。

| 样本 | 源分辨率 | 解码结果 | `isSampled` |
| --- | --- | --- | --- |
| 真实图 `羽毛笔.jpg` | 10800 × 10800（1.166 亿像素） | 4096 × 4096 | true |
| 真实图 `20211023_…_p0.jpg` | 7728 × 4408 | 4096 × 2336 | true |
| 合成图 `img-huge-5000x40000.jpg` | 5000 × 40000（2 亿像素） | 512 × 4096 | true |
| 合成图 `img-strip-2000x20000.png` | 2000 × 20000 | 410 × 4096 | true |

**必须遵守的硬规则：图片请求不得指定原始尺寸。** 在 Pager 中显式使用 `Size.ORIGINAL` 时，6000 × 4000 的图解码失败并记录 `failed to allocate hardware Bitmap!`；去掉尺寸参数后同一张图解出 1200 × 800，失败消失。真机上 26 张图（含上述全部大图）连续翻页零失败，进程未被回收，`app start` 计数为 0，堆稳定在 11–14 MB / 256 MB。

**视频：真机与模拟器逐项一致**。三个 AVI 变体（MPEG-4 SP、Xvid、DivX 3）均可播放并可 seek，与「AVI 可能不可用」的早期猜测相反。

| 格式 | 结果 | 进度拖动 |
| --- | --- | --- |
| MP4 / H.264、HEVC、AV1 | 可播放 | 可拖动 |
| MOV / H.264 | 可播放 | 可拖动 |
| MKV / H.264、HEVC | 可播放 | 可拖动 |
| WebM / VP9 | 可播放 | 可拖动 |
| TS / H.264 | 可播放 | 可拖动 |
| 3GP / H.263 | 可播放 | 可拖动 |
| AVI / MPEG-4 SP、Xvid、DivX 3 | 可播放（DivX 3 无 `videoFormat` 上报） | 可拖动 |
| FLV / H.264 | 可播放 | **不可拖动**，seek 后停在 0s |
| WMV / msmpeg4v2 | **无法播放**，`ERROR_CODE_PARSING_CONTAINER_UNSUPPORTED` | 不适用 |

产品口径（已确认）：不为不常见格式做特殊兼容，FLV 只播不拖，WMV 失败时提示并交给系统应用。

### 已知待修缺陷

真机上视频播放中按 Home 回到后台，**声音仍在继续**。探针里 `ON_STOP` 只调用了 `pause()` 而没有释放播放器。实现时必须按规范 5.1 的要求，在应用进入后台时释放播放器；验收标准是「后台完全无声」，不能只验证「已暂停」。

### 尚未验证

- 后台静音的正确做法需要重新验证（先确认释放是否足够）。
- API 26–28 设备上的行为（AV1 需要 API 29+，HEIC 需要 API 28+，目前只有 API 36 一个验证点）。
- HEIC/HEIF 解码（缺样本，本机无法生成）。
- 真实老资源文件（AVI 样本为合成，DivX 3 不等于真实资源站的 Xvid/DivX 文件）。
- release 构建的体积增量（探针 debug 包为 19.42 MB，不能代表 release）。
- 双指缩放的跟手程度由用户在真机上确认「顺畅、能高清查看」，但没有客观指标记录。

## “从系统相册隐藏”实现与验证

设置中的开关只管理 Library 根目录 `.nomedia`：

- 开启时创建 `Library/.nomedia`；关闭时移除该文件；未接入 Library 时不可操作。
- `storage/LibraryTree.setSystemGalleryHidden` 是唯一写入点，返回写入后由 provider 读回的真实状态，界面不显示未经确认的状态。
- 开关决策抽成纯函数 `markerAction` 并配有单测：目标状态与现状一致时不动作，名为 `.nomedia` 的目录按冲突处理、绝不删除。
- ViewModel 串行化该操作，重复点击不会并发写入，因此不会产生 `.nomedia (1)`。
- 不修改、改名、移动、删除或覆盖任何原始媒体；不主动删除 `MediaStore` 已有记录。
- 开关状态由当前 Library 中 `.nomedia` 是否存在推导，不另存本机偏好。

小米官方说明路径任一层存在 `.nomedia` 时，该路径下图片不会被系统媒体服务记录：[KA-09388](https://www.mi.com/global/support/article/KA-09388/)。

### 真机验证（2026-09-20，本轮）

设备小米 `23127PN0CC`（`houji`），Android 16，澎湃 OS `3.0`（`V816`）。经 SAF 文件选择器接入探针 Library `/Download/RemLibraryProbe/`（含 `相册/` 与 `画集/测试作者-测试项目/`），全部操作通过界面点击完成：

| 验证项 | 结果 |
| --- | --- |
| 开→关、关→开连续 4 轮 | 每轮恰好 1 个标记文件，状态与界面一致 |
| 连续 5 次快速点击 | 始终只有 1 个 `.nomedia`，无 `.nomedia (1)` |
| 重启应用 | 开关恢复为开，状态来自 Library 而非本机偏好 |
| 应用外删除 `.nomedia` 后重启 | 开关显示为关，证明状态由磁盘推导 |
| 开启后向两条分支新增媒体并重新扫描 | 磁盘 8 个文件，`MediaStore` 记录 0 条 |
| 关闭后重新扫描 | 8 条记录全部恢复 |

补充结论与边界：

1. 应用创建的 `.nomedia` 是普通文件（本机 provider 写入 44 字节父目录路径）；标记的作用只取决于文件是否存在，空文件行为相同。
2. 本机重新扫描会清除 `.nomedia` 目录下已经建立的 `MediaStore` 记录，移除标记后这些记录会随扫描恢复。此效果强于此前记录，但**仍需系统重新扫描**；应用自身不触发扫描，所以刚切换开关时已有记录可能继续显示，界面提示按此表述。
3. 小米 Gallery 界面本身的即时隐藏/恢复表现未做独立 UI 验证，本轮只验证了底层 `MediaStore` 记录。

验证用探针目录、推送脚本与临时文件已全部从设备删除；`MediaStore` 图片记录数已回到验证前的 77 条基线。

## 模拟器验证（2026-09-20，本轮）

真机拔除后改用 Android 16（API 36）模拟器 `Rem_API_36` 继续验证。测试 Library 由 WSL 用 Pillow/piexif/ffmpeg 生成，共 827 个文件，覆盖各媒体容器、元数据组合、异常命名和 600 项长列表，经 SAF 选择器接入。

### 已确认可用

| 项目 | 结果 |
| --- | --- |
| SAF 接入规模 | 827 个文件；首次全量扫描 16.4s，丢弃缓存后重扫 6.7s，增量重扫 640–750ms |
| `待分类/` 边界 | 根目录可见但不被扫描，827 条条目中不含其内容 |
| EXIF 拍摄时间 | `DateTimeOriginal` 优先，缺失时退到 `DateTime`，再缺失用文件修改时间 |
| GPS 地点 | 规范 EXIF 能读出经纬度；piexif 写出的畸形 GPS IFD 被 ExifInterface 正确拒绝 |
| 目录规则 | 项目列表显示作者/项目与计数；不合规文件名被报告为违规 |
| 右侧滑块 | 点击与拖动都能跳转，拖动时显示序号 |
| 调用系统查看器 | 图片与视频均交给系统应用打开 |
| 无可用应用 | 禁用查看器后提示「系统没有可以打开 X 的应用」 |
| 缩略图 | 图片与视频缩略图均正常渲染 |

### 本轮发现并修复的缺陷

| 编号 | 问题 | 修复 |
| --- | --- | --- |
| D1 | 一次完全复用缓存的扫描后，目录列表缓存不再失效，「重新扫描」再也看不到新增文件——实测 4ms 返回 823 条却什么都没读，只有重启应用才恢复 | 每次扫描开始时清空列表缓存；该缓存只用于避免同一次扫描重复列目录 |
| D2 | 视频拍摄时间从未读出，全部按文件修改时间排序 | `METADATA_KEY_DATE` 同时接受扩展与紧凑两种 ISO-8601；并把 MP4 的 1904 纪元当作「未设置」而不是日期 |
| D3 | 滑块标签被轨道的 34dp 宽度约束并溢出屏幕，只剩首字符 | 允许标签超出轨道宽度，改为靠右向左展开 |
| D4 | 拖动超过 900ms 后标签自行消失，手指仍在移动 | 计时随标签更新重启，拖动期间保持显示 |
| D5 | 只有违规列表变化时索引不写回，持久化的违规信息会过期 | 违规变化也写回索引 |
| D6 | `encodeDefaults=false` 让 `version` 字段从不写入，索引版本校验永远不触发 | 版本字段始终编码；缺少该字段的旧文件按旧版本处理并被丢弃重扫 |

D6 是 D2 的修复一开始不生效的原因：旧缓存不会被判定为过期。六项修复后均已在本轮模拟器上复验。

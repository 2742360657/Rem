# Rem 产品规范

> 本文件只回答：Rem 为什么存在、用户的媒体如何理解、软件应该提供怎样的管理与观看体验。
> 不描述 Kotlin 包、SQLite 表、具体 JSON 字段或某次开发进度。

2026-09-18 用户明确确认：下述六类媒体、观看习惯及四条产品主线都是正式需求，不是候选设想。本文规定目标；实现程度和验证证据只在 [STATUS](STATUS.md) 登记，不能将目标提前写成已有功能。

## 1. 产品定位

Rem 是面向 Android、本地大容量媒体库和移动存储的媒体管理与阅读/播放工具。

它管理的是“用户拥有的普通文件 + 可携带的逻辑关系”，而不是把媒体封闭进专有数据库。

核心目标：

1. 原媒体始终保持普通文件，可脱离 Rem 使用；
2. `.gallery/` 保存逻辑结构和人工决定；
3. Library 可以整体移动并快速在另一台 Android 设备重新接入；
4. Android 端只做可靠、廉价、弱识别；
5. 主要生产力来自高效率的批量管理、批量编辑和安全整理；
6. 复杂、大规模、规则化整理由本地 Agent 承担；
7. 阅读/观看体验必须围绕真实的媒体关系，而不是围绕文件扩展名。

当前不把 Rem 做成：
云同步服务、多用户系统、在线流媒体平台、推荐系统、AI 内容识别器、图片/视频编辑器或 PC 媒体播放器。

## 2. 三种角色

### 2.1 Android App

负责：

- 接入 Library；
- 快速清点；
- 弱识别并给出可解释建议；
- Inbox 确认；
- 单项与批量元数据管理；
- Group / Series / Edition 等逻辑关系编辑；
- 图片、漫画、视频的移动端观看；
- 安全的物理 Organizer；
- 从 `.gallery/` 快速恢复用户决定。

不负责：
对整个 Library 做复杂、高风险、强推断式自动整理。

### 2.2 用户

用户的人工决定优先级最高。
用户可以在 App 中确认、批量修改，也可以让本地 Agent 整理后再在 App 中直接使用结果。

### 2.3 Library Agent

本地 Agent 面向整个 Library 做高质量批量整理：

- 读取目录结构和已有 `.gallery/`；
- 依据固定规则识别作者、作品、系列、章节、标签等；
- 批量建立或修正逻辑关系；
- 给出整理说明、歧义和证据；
- 必要时生成物理整理计划，但不能绕过安全边界。

详细规则见 `LIBRARY_AGENT.md`。

## 3. 用户真实媒体模式

Rem 的逻辑模型必须覆盖以下常见情况。

### 3.1 单本漫画 / 单个顺序图集

```text
作品目录/
  001.jpg
  002.jpg
  003.jpg
```

特点：

- 一个目录就是一个完整 Work；
- 内部媒体有明确阅读顺序；
- 可能属于更高层 Series，但本身没有 Chapter 层。

### 3.2 连载漫画

可能是：

```text
作品/
  第001话/
    001.jpg ...
  第002话/
    001.jpg ...
```

也可能是：

```text
作品/
  第001话.cbz
  第002话.cbz
```

产品语义：

- “作品”与“章节/话”是不同层级；
- 章节之间有明确连续阅读顺序；
- 不能因为物理上都是子目录就把“章节”和“独立作品”混为一谈。

### 3.3 实拍照片和视频

核心入口是时间轴：

```text
时间
  ├─ 图片
  └─ 视频
```

用户应能：

- 图片视频混合按时间查看；
- 仅看照片；
- 仅看视频；
- 从单个媒体回到其时间上下文。

界面不强迫用户先创建 Work / Series 才能看照片。Library 内需要保存人工决定的单个媒体仍映射到现有 Work + Edition + Asset；时间轴直接呈现媒体，不额外暴露这层管理结构。系统相册尚未复制导入的内容仍属于系统媒体来源。

### 3.4 收藏相册 / 梗图 / 表情包 / 截图

重点是分类浏览，可能存在多级目录，但逻辑分类不等同于物理目录。

需要支持：

- Album / Collection；
- Tag；
- 多层视觉导航；
- 同一媒体被多个逻辑视图找到，而不复制文件。

### 3.5 作者作品集 / 写真集

常见结构：

```text
作者/
  作品01/
    图片/视频
  作品02/
    图片/视频
```

也可能是：

```text
作者/
  video01.mp4
  video02.mp4
```

产品语义：

- 作者是元数据和查询维度；
- Work 可以由图片、视频或二者混合组成；
- 单个视频也可以直接是一个 Work；
- 作者目录不是永久实体关系的充分证据。

### 3.6 影视 / 动画剧集

```text
作品/
  EP01.mp4
  EP02.mp4
```

或：

```text
作品/
  Season 1/
  Season 2/
```

需要表达有序连续观看。
Season / Episode 与漫画 Volume / Chapter 在底层可以共享“有序位置”的思想，但 UI 文案按媒体类型呈现。

## 4. 核心逻辑对象

### Asset

物理来源。
文件、目录、压缩包等都可以是 Asset。

### Work

用户认为是“一个可命名、收藏、阅读或观看的内容单位”。

例如：

- 一本漫画；
- 一期写真；
- 一个图片集；
- 一段独立动画；
- 一集视频；
- 一个混合图片/视频作品。

Work 不要求只有一种媒体格式。

### Edition

同一个 Work 的一个取得版本。
例如目录版、CBZ 版、附带视频版、不同下载源。

### Group

“这些 Work 适合一起浏览”。

适合：

- 一期写真中拆出的若干逻辑 Work；
- 图片与视频混合浏览集合；
- 用户手动建立的收藏组。

Group 不表示阅读先后，也不表示同一 Work 的版本。

### Series

“这些 Work 具有明确的顺序关系”。

适合：

- 某个系列的多本漫画；
- 连载作品的多个章节；
- 动画/影视多集；
- 需要从一个 Work 连续进入下一个 Work 的内容。

Series 不是“同作者全部作品”的代名词。

### Creator / Author

作者、创作者、制作方等元数据维度。
它主要用于筛选和聚合，不必为了“作者书架”制造新的实体关系。

### Album / Collection / Tag

面向分类和检索的维度。

- Album 更偏相册/浏览上下文；
- Collection 表示用户定义的归类；
- Tag 表示可多选的横向标签。

三者不应强迫物理文件移动。

## 5. 层级是可选的，不是固定五层

可能存在：

```text
Work -> Media
```

或：

```text
Series -> Work -> Media
```

或：

```text
Series -> Work/Chapter -> Media
```

或：

```text
Creator(query) -> Series -> Work -> Media
```

也可能只有：

```text
Timeline -> Media
```

因此 Rem 不应要求所有媒体都进入固定：

`作者 → 系列 → 作品 → 章节 → 文件`

这是浏览关系，不是强制目录树。

## 6. 四种主要浏览模式

### 6.1 层级浏览

```text
作者/筛选
  → 系列
  → 作品
  → 内容
```

适合漫画、写真、作者作品、动画和影视。

### 6.2 时间浏览

按拍摄/创建时间浏览照片与视频。

### 6.3 分类浏览

按 Album、Collection、Tag 或用户分组浏览。

### 6.4 自由发现

随机或跨库浏览单个媒体，然后能够反向找到：

```text
Media
  → Work
  → Series
  → Creator / Tag / Collection
```

典型场景：
随机翻写真图片，发现喜欢的内容后进入其完整一期作品，再查看同作者或同系列内容。

## 7. 阅读与观看语义

### 完整阅读一个 Work

- 图片漫画按稳定页序；
- 视频保存播放位置；
- 完成状态是明确状态，不用“打开过最后一页”简单推断。

### 连续阅读一个 Series

- Series 自己拥有顺序；
- 用户从 Series 入口打开时才建立连续阅读上下文；
- 从搜索单独打开一个 Work，不应突然跳入整个系列。

### 随机浏览

随机展示的是 Media，但必须保留来源关系，随时可以进入完整 Work。

## 8. 识别哲学

扫描分为：

1. Discovery：发现有什么；
2. Suggestion：基于低成本证据提出建议；
3. Decision：用户或明确规则的 Agent 作决定。

不能把三者合并。

Android 可使用：

- 目录名；
- 自然编号；
- ComicInfo；
- 稳定下载 ID；
- EhViewer / Pixiv 等明显来源标记；
- 章节/集数命名；
- 文件类型与叶子目录结构。

但这些都只是证据。
目录名“像作者”、父目录“像系列”不等于永久关系。

## 9. 批量管理是第一等功能

任何高频管理动作都应优先支持选择集：

- 批量接受/忽略 Inbox；
- 批量作者、Tag、Collection；
- 批量加入/移出 Group；
- 批量加入/移出 Series；
- 批量编号；
- 批量收藏；
- 批量逻辑回收站；
- 批量修正领域类型；
- 批量选择封面/规则化标题（适合时）。

要求：

- 批量操作与单项操作使用同一领域规则；
- 显示影响范围；
- 冲突项单独报告，不悄悄吞掉；
- 对便携元数据尽量一次提交；
- 不把批量元数据操作偷偷升级成真实文件变更。

## 10. 物理目录与逻辑关系分离

原则：

```text
物理目录 = 来源与线索
逻辑模型 = 用户真正如何理解和浏览内容
```

因此：

- 改 Series 不必移动文件；
- 改作者不必重命名目录；
- 改 Collection 不必复制文件；
- 换设备不因路径根变化而丢失关系。

只有用户显式确认的物理操作才改变实际文件结构，包括 Organizer、页序保存并编号、复制导入和永久删除；各自执行预览、冲突检查与适用的恢复流程。

## 11. 跨设备与移动 Library

必须成立：

1. Library 整体移动后，便携路径仍然有效；
2. 新设备接入时先读 `.gallery/`，立即恢复逻辑库；
3. 原媒体还没扫描到时，Work 仍然可见并可管理；
4. “媒体不在本机”是正常可达状态；
5. 本机索引或缓存损坏不能反向污染 `.gallery/`；
6. 缩略图、URI、扫描 checkpoint 不应成为便携真相。

用户从系统目录选择器确认返回后，接入必须显示当前阶段；授权或初始化失败须保留明确错误及重新选择入口，不能只短暂提示后回到空白初始状态。目录查询和授权处理不得阻塞界面线程。

## 12. 产品判断优先级

遇到设计冲突时按此顺序：

1. 不丢用户人工决定；
2. 不误改原媒体；
3. Library 可携带、可恢复；
4. 语义清晰且关系唯一；
5. 批量管理效率；
6. 浏览/阅读体验；
7. 自动识别便利；
8. 实现简单。

实现简单不能压过前七项。

## 13. 已确定的歧义处理

- **作品与章节**：单本漫画是 Work；连载每话也是 Work，整部连载通过 Series 排序展示。Chapter / Episode 是位置及界面文案，不新增独立实体，也不新增固定五层树。更复杂的嵌套系列暂不扩展 Schema。
- **作者与系列**：作者入口是查询，展示该作者的系列和未归系列作品；允许多作者。作者目录不自动生成 Series，也不因目录迁移失去归属。
- **混合写真**：用户眼中的一期内容必须有完整浏览入口。当前优先沿用图片集 Work + 视频 Work + Group；格式允许多 Asset Edition，但完整混合 Work 播放不能因格式能表达就宣称已实现。不为界面整齐自动合并已有 Work。
- **分类与多级目录**：保留物理目录浏览，逻辑分类优先用 Collection / Tag / Group。Album 暂是相册浏览语境，不新增便携 Album 实体；多级物理目录不强制映射为嵌套 Collection。
- **随机写真**：在用户选择的库、作者或分类范围内随机浏览图片页，保留 Work、Group、Series 和作者来源；“看这一期”回到完整一期，“同类”进入明确的作者/标签/分类结果，不做 AI 相似推荐。默认排除 Inbox、忽略、回收站和不可读来源；随机顺序不写回作品页序或系列顺序。
- **照片时间轴**：优先可信拍摄时间，缺少时回退媒体可用时间并可辨别来源；所有内容、仅照片、仅视频是同一时间上下文的过滤。手动纠正时间若引入新便携字段，应单独设计格式，不能只存 SQLite。
- **批量编辑**：追加、替换、清空是不同动作；显示范围和冲突，显式清空也保留人工锁。实现共享规则，不把当前 append-only 当成产品终点。
- **连续阅读**：系列入口建立顺序上下文；搜索或随机打开单个作品不擅自跳系列。完整阅读、完成标记、继续阅读和重读行为保持一致。
- **跨库管理**：每个 Library 独立提交并报告结果，不宣称多个 Library 之间具备全局原子性；实体关系不引用其他 Library 的 ID。

这些是用户授权 Agent 消歧后的当前决定。以后改变时在本节修改原因，并同步格式、状态及验收；不能从临时 handoff 另起解释。

## 14. 需求与验收登记

编号永久保留。用户补充先归入已有条目；独立需求再新增编号。这里登记要求与验收，进度只在 [STATUS](STATUS.md) 维护。

| 编号 | 已确认要求 | 最小可观察验收 |
| --- | --- | --- |
| R01 | 单本顺序漫画，可能属于多本系列 | 一个图片目录/支持的容器作为一个 Work，按自然或明确页计划读完；加入 Series 不改媒体 |
| R02 | 多话连载漫画与多集影视 | 每话/集独立进度，季/集/卷/章可选；按系列顺序继续和重读，图片目录与 ZIP/CBZ 统一；视频连续观看单独验收；其他容器按格式逐项声明支持，未知格式进 Inbox |
| R03 | 实拍照片视频时间轴 | 混排和照片/视频过滤共享排序及返回上下文；缺少拍摄时间有确定回退；保存人工决定后可换设备恢复 |
| R04 | 相册集、梗图、表情包、截图分类 | 保留多级目录浏览，Collection/Tag/Group 可跨目录找到同一内容，不复制、不移动媒体 |
| R05 | 作者作品集、混合写真、纯视频作者 | 作者聚合含系列和独立作品；一期图片视频有完整入口；独立视频可直接播放，不强制建 Series |
| R06 | 随机写真发现并回到完整内容 | 限定范围随机翻页，能进入原 Work/一期 Group、作者或明确分类，返回保留随机上下文，作品顺序不变 |
| R07 | 完整 Work / Series 阅读与观看 | 完成不等于恢复末页；继续、重读、下一话、退出和返回可预测；返回保留原列表位置；图片缩放与连续滚动互不争抢；视频可主动切换横屏/全屏并恢复方向；混合目录打开视频不得跳到其他图集 |
| R08 | 优越的批量管理和编辑 | 选择集可批量接受/忽略、收藏、分类、作者/Tag/Collection 追加/替换/清空、关系管理及逻辑回收站；报告冲突，提交保留并发人工修改与人工无值 |
| R09 | Android 只做基础弱识别 | 发现、建议、决定分开；含证据且成本有界；低置信和不支持内容可处理，人工锁不被识别覆盖 |
| R10 | 固定且独立的 Library Agent 整理能力 | 无 Android 数据库也能按库内说明和明确规则整理；有备份、校验、字段合并、歧义报告、稳定来源和安全提交；App 可读回结果 |
| R11 | Library 移动及不同 Android 设备快速恢复 | 原根改变不重写路径；仅 .gallery 恢复关系和决定，媒体补全不阻塞逻辑库；缺失可管理；在真实库上记录接入、扫描耗时及设备，目标不凭空定秒数 |

需求不因排在后面而失效。所有 R01–R11 同时受便携真相、媒体安全、人工优先约束。未完成能力不得提前进入用户指南。

## 15. 读取性能与媒体安全要求

- 2026-09-19 用户明确补充：所有长列表/网格和阅读界面需可发现的快速滚动/定位控件；漫画支持输入页码跳转，列表可按项目位置快速定位。观看后返回保留原目录、筛选和滚动锚点，不自动回到顶部。
- 当前打开的本地内容优先于后台缩略图与扫描/补全；后台工作并发有界且可取消，不能让当前打开持续无反馈转圈。打开中显示阶段，读取失败保留可重试错误。以真机冷/热打开与后台繁忙场景记录耗时及调度证据，不凭空保证秒数。

- 比较分为已有索引、显式页清单/哈希、可选像素建议三层；像素层是目标中的可选扩展，不自动认定相同，不触发删除。重复比较复用未变来源的本机结果。
- 阅读按视口解码；压缩包支持中央目录随机访问，不逐页重读全包。缓存与预览可清除，正在使用的大归档不能因自身大小被淘汰。
- 普通删除是逻辑回收站；期限仅提醒，无后台永久清除。永久删除拒绝未经确认的共享/嵌套/多来源删除，恢复机制不能承诺恢复已删字节。
- 独立作品、分组成员或系列成员缺失只影响本机可读性，不改变人工关系。
- 图片/漫画控件可隐藏，缩放围绕焦点并钳制边界；连续漫画宽度适配、放大锁页、退出缩放回到可预测位置。密度和返回行为参考 EhViewer / MT 管理器，局部改进不触发无边界 UI 重写。
